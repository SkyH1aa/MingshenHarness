# 编程任务补充规则

## 开始前

- 找到项目根目录、构建方式和测试入口。
- 检查 Git 状态，识别脏工作区和用户未提交的改动。
- 阅读最相关的实现、类型定义、测试和配置。不要只读 README 就开始改。
- 明确本次改动的验收条件和影响范围，并定位入口、调用方、相邻测试及所有权边界。复杂任务先建立简短执行顺序，简单修复直接完成。
- 如果任务描述与代码现状矛盾，以可验证的代码和用户澄清为准，不猜测。

## 修改时

- 保持现有模块边界和公开契约。跨边界修改必须有明确原因。
- 不进行用户没要求的全局重构、依赖升级、格式化或重命名。
- 优先修复根因，不用掩盖症状的 try/catch、静默回退或宽泛类型断言。
- 错误处理应保留上下文，不吞掉失败，也不向用户泄露密钥或内部敏感数据。
- 对并发、取消、重试、超时、资源清理和崩溃恢复进行显式设计。
- 数据解析使用结构化 API，不用脆弱正则处理 JSON、HTML、YAML 或配置。
- 不把未经校验的外部内容插入 shell、SQL、HTML、文件路径或请求头。
- 新依赖需要有明确用途，并考虑 Windows 打包、原生模块和许可证影响。
- 前端改动遵守 `DESIGN.md` 和现有组件规范，保留键盘、焦点、错误、空状态和响应式行为。
- 修复缺陷时先建立可复现证据，再定位根因。若无法先写失败测试，至少保留可重复的原始失败路径，并在修改后验证同一路径。
- 涉及数据、并发、持久化、权限、迁移和外部副作用时，同时检查失败、重试、取消、重复执行、部分成功和恢复路径。
- 代码风格、抽象层级和错误语义服从周边实现。不要因个人偏好重写正常代码，也不要用过宽断言、静默降级或捕获后忽略来掩盖未知状态。

## 验证

- 修改后先检查 diff，再运行最相关的测试和构建。
- 按风险从小到大验证：先定位性测试或最小复现，再运行相邻测试、类型检查、Lint、构建或真实界面检查。较大改动再扩展到共享测试和发布路径。
- 修复失败测试时确认测试本身没有掩盖真实需求。
- UI 改动至少进行一次真实渲染检查；Electron 应用还要检查打包后的行为。
- 不能运行测试、构建或真实模型调用时，说明缺失的依赖或凭据，不把未验证结果说成通过。
- 验证失败时判断是实现、测试夹具、环境还是既有缺陷。只有证据充分才调整测试；不能用放宽断言、删除用例或提高通用超时替代根因修复。

## 交付前审阅

- 对照最初目标和 diff 检查是否遗漏正常路径、边界条件、错误提示、文档/配置同步及数据兼容。
- 检查新增代码是否有真实调用路径、正确的类型和权限，以及是否留下临时日志、调试入口、后台进程、构建产物或无关改动。
- 汇总实际行为、关键文件和验证证据，并明确未运行项与残余风险。除非用户要求，不附加逐行代码讲解或冗长改动清单。

## 交付

- 汇总时说明核心改动、验证结果和仍然存在的风险。
- 文件引用应准确，不引用不存在或未修改的文件。
- 用户要求提交或发布时才执行这些动作。
