# Mingshen Harness 运行治理

适用版本：1.3.7 · Windows 10/11 x64

本文说明统一运行记录、幂等请求、事件续接、重启恢复、模型连接等待、管理策略、工具结果校验和计划任务认领。源码已经提供相应接口，集成验收与正式安装包状态仍以当前验证记录为准；本文不把单元测试、静态源码或接口约定写成真实 Office、付费供应商和安装升级均已通过。

## 设计原则

1. 用户请求先形成可恢复的运行记录，再进入附件处理、命令预处理、模型请求和工具执行。
2. 状态、停止和恢复都以准确 `runId` 为边界，不能把停止操作误用到同一会话的下一轮。
3. 运行历史、已提交消息、任务和验证证据保存在本机。断线或重启后先核实状态，再决定是否继续。
4. 内置安全边界、机器策略、应用策略、模式和项目设置叠加生效。限制只能收紧，不能由项目文件、Agent 提示词或 `full_access` 放宽。
5. 工具执行成功、输出结构校验、业务验证和办公交付验证是不同状态，不能互相替代。

## 运行状态

设计目标是让主界面、快捷 Chat、桌宠、本地 API、SDK 和 ACP 使用同一持久运行来源。当前源码已提供统一 `RuntimeService`、事件和接口，但这些表面的状态一致性、断线恢复和取消竞争仍需按本页末尾的边界完成联测。

| 状态 | 含义 | 是否终态 |
| --- | --- | --- |
| `accepted` | 请求已持久接纳并分配 `runId`，尚未开始准备 | 否 |
| `preparing` | 正在处理附件、命令预处理、配置或上下文准备 | 否 |
| `running` | 模型或受管工具链正在推进 | 否 |
| `waiting_approval` | 正在等待人工权限审批 | 否 |
| `waiting_user` | 正在等待 Agent 提问的回答 | 否 |
| `completed` | 正常运行完成 | 是 |
| `failed` | 运行失败，错误和诊断可回看 | 是 |
| `interrupted` | 用户停止、崩溃恢复或明确中断 | 是 |
| `blocked_policy` | 被管理策略阻止，未进入受限制动作 | 是 |

`blocked_policy` 不是失败重试的替代名称。它表示宿主策略主动拒绝，调用方应先读取有效策略和拒绝原因，不能自动改换路径或放宽权限后重放。

## 请求接纳与幂等

- 新接口要求调用方为同一请求体提供唯一的 `Idempotency-Key`。键按会话隔离，建议使用 UUID。
- 同一会话中，相同幂等键和相同请求载荷返回原运行，不再次执行。
- 同一幂等键搭配不同请求载荷返回 `409 IDEMPOTENCY_CONFLICT`。
- 接纳记录包含 `turnId`、`runId`、请求摘要、来源、时间和重复标记。重复请求不能创建第二个模型请求或工具副作用。
- 新请求在同一数据库事务中持久化运行行、接纳记录和 `runtime.status` 的 `accepted` 事件；提交成功后才向主界面、快捷 Chat、桌宠和外部事件流发布接纳通知。重复请求只返回原运行与现有游标，不额外制造第二个 `accepted` 生命周期事件。
- 运行状态变更与对应生命周期事件使用同一 SQLite savepoint。事件写入或派发前的持久化检查失败时，状态更新必须回滚，不能留下“状态已变但历史缺事件”的运行；提交后的传输订阅失败只记录诊断，不重做状态变更或工具副作用。
- 桌面界面与外部接口复用同一个接纳流程。接纳失败时不应把界面上的“发送中”状态当成已运行。
- 请求正文上限由本地 API 统一限制。超出上限的请求在进入 ChatService 前拒绝。

## 事件与断线续接

持久事件用于生命周期、消息提交、审批、用户问题、任务和验证等重要变化。正文与思考增量属于临时传输事件：实时 SSE 帧没有持久 `id:`，也不推进客户端保存的事件游标；断线后不保证重放。最终持久消息和会话快照才是权威内容。

事件流支持：

- 查询参数 `after=<eventId>`。
- SSE `id:` 字段。
- 重连请求头 `Last-Event-ID`；存在时优先于查询游标。
- `sessionId` 和 `runId` 过滤。
- 有界分页和历史事件回放。

服务端找不到请求游标时返回 `410 CURSOR_EXPIRED`，响应包含 `snapshotRequired: true`、请求游标和最早可用游标。客户端必须重新取得会话快照，再从新快照的 `eventCursor` 续接；不能从零开始假定所有历史仍存在。

默认事件保留策略：

| 项目 | 默认值 |
| --- | --- |
| 最长时间 | 30 天 |
| 总容量 | 256 MiB |

清理历史传输事件不会删除运行快照、会话消息或办公回执。事件被清理后，客户端通过会话快照恢复可交付状态。

## 崩溃恢复与人工继续

应用启动时会检查未结束的运行。`accepted`、`preparing`、`running`、`waiting_approval` 和 `waiting_user` 在重启后标为 `interrupted`，并记录 `runtime.recovered` 事件。

恢复不会自动重放模型请求、未完成工具参数或已经开始的命令。用户点击继续后：

1. 先读取会话快照、运行状态、任务、审批和最近事件。
2. 核实中断前是否可能已有文件、命令、远程服务或 Office 副作用。
3. 对确定完成且证据可核验的步骤保留结果。
4. 对可能已执行的写操作先检查实际状态；不自动重试，直到确认没有重复副作用或由用户明确处理。
5. 从下一个未完成步骤继续，而不是重新创建整段任务。

网络重连只重试失败的模型请求，不重新执行已经完成的工具。网络恢复不等同于应用重启恢复，也不提供任意外部服务的 exactly-once 保证。

## 模型连接等待

设置 → 运行与集成 → 运行治理提供模型连接等待检测：

| 检测 | 默认值 | 重置条件 |
| --- | ---: | --- |
| 首个有效响应 | 5 分钟 | 收到有效正文、思考或工具参数 |
| 流空闲 | 15 分钟 | 每次有效正文、思考或工具参数推进 |

规则：

- 有效值为 0 到 1440 分钟；0 关闭对应检测。
- 心跳、空响应、用量统计和重复空片段不重置流空闲计时。
- 等待工具、审批或用户输入期间不计入模型流空闲。
- 超时沿用当前模型请求的自动重试预算；用户主动取消不重试。
- 超时或截断的模型输出不能执行未完成的工具调用。
- 这是单次模型请求的网络等待保护，不是任务、SubAgent、命令、审批或 Office 检查的总运行时限。主 Agent 和 SubAgent 都没有固定总运行寿命。

## 两层管理策略

机器管理员策略位于：

```text
%ProgramData%\MingshenHarness\managed-policy.json
```

应用策略由当前 Windows 用户在设置中配置。两层都使用版本 1 的 JSON 结构，实际有效策略还会叠加内置安全边界、Agent 模式、项目信任和执行环境限制。

最小示例：

```json
{
  "version": 1,
  "capabilities": {
    "network.request": "ask",
    "command.execute": "deny"
  },
  "allowedExecutionModes": ["worktree", "docker"],
  "office": {
    "minimumStatus": "rendered",
    "maxRepairRounds": 2
  }
}
```

决策语义：

- `deny` 优先，低层策略不能把它改回 `ask` 或 `allow`。
- `ask` 要求在实际调用入口取得对应批准；没有批准不能执行。
- `allow` 只表示管理策略没有额外阻止，不绕过内置边界、Profile、审批、隔离、写入锁或项目信任。

可限制的宿主能力包括供应商与图片请求、网络与网页、浏览器、文件、工具、命令、交互终端、MCP、Skill、插件与 Hook、扩展市场更新、子 Agent、Office 验证和开发者 API。创建交互终端必须在启动 Shell 或其用户 profile 之前先检查 `command.execute`；`deny`、`ask` 和无效策略均 fail-closed，不能弹出空终端，也没有可绕过启动 Shell 的交互审批旁路。

依赖管理和应用更新也使用逐阶段门禁，而不是只在页面入口检查一次。自动或手动依赖检查若会发起网络请求、验证签名、执行安装器、探测命令或启动 Docker，网络、命令和安装阶段会分别重新读取有效策略；显式用户批准不能覆盖机器层或应用层 `deny`。更新元数据请求、ZIP/安装器下载、启动安装器前后也逐次检查；应用在销毁数据库前保留原始用户策略快照，并在实际 `app.relaunch` 前重新读取机器策略、完成最终 `command.execute` 检查。策略损坏、检查失败或拒绝时跳过安装器并正常退出，不能用旧批准或旧 revision 继续执行。

有效策略查询同时返回整体 `revision`、`status.machine`、`status.user` 和 `capabilityDecisionsByLayer`。机器层包含策略文件路径与该层 revision，应用层标记为当前用户配置；两层分别列出已声明的能力决策。实际拒绝的 `sources`（开发者 API 中为 `policySources`）进一步给出触发层、该层 revision、规则原因和机器策略路径。运行记录里的 `policyRevision` 是接纳时快照；执行过程中策略发生变化时，当前拒绝信息以该次调用的 `revision`/`sources` 为准。

运行记录同时保存最近一次实际拒绝的 `lastPolicyDenial`，其中包括 `revision`、`code`、`reason`、`scope`、`sources` 和发生时间。更新这条元数据不会覆盖接纳时的 `policyRevision`，也不会改变运行当前状态。拒绝元数据和 `runtime.policy_denied` 事件在同一事务中持久化；临时事件达到默认 30 天或 256 MiB 保留边界并被清理后，运行查询和会话快照中的最新拒绝信息仍保留。字段按源码上限截断，不包含或替代完整策略文件。

机器策略文件不存在是正常状态。文件存在但出现以下任一情况时，有效策略状态变为无效：

- 不是普通文件，或通过符号链接提供。
- 无法读取或超过 256 KiB。
- JSON 损坏、包含未知字段、版本不支持或值超出规定范围。
- 未通过当前实现的结构校验。

策略无效时暂停新的模型、工具、扩展、Office 验证和开发者派发；历史查看、诊断、停止、清理和修复设置仍可用。开发者 API 经过 Bearer 认证的现有历史读取、会话快照、运行查询和有效策略查询保持只读可用，以便定位策略错误；该诊断旁路不允许写请求、计划认领或 Office 检查。修复文件后，下一次调用前会重新读取，不需要重启。

策略治理的边界：

- 它是宿主能力治理，不是 Windows 沙箱、EDR 或文件系统 ACL。
- `full_access` 不能放宽 `deny`、无效策略或内置安全边界。
- 已经发出的网络请求、已启动的进程和远程副作用不能因随后修改策略而撤回。
- 应用不会自动修改 `%ProgramData%` 的 ACL。机器策略目录和写入权限应由管理员使用组织认可的部署方式保护。

## 工具结果契约

新的统一 `ToolOutcome` 同时表达：

| 字段 | 作用 |
| --- | --- |
| `status` | `success`、`partial`、`failed`、`denied`、`cancelled` 或 `unverified` |
| `effect` | `none`、`confirmed` 或 `uncertain` |
| `retryable` | 是否允许按策略重新尝试 |
| `codes` | 稳定的原因码 |
| `validation` | `validated`、`not_declared`、`invalid` 或 `unverified` |
| `evidence` | 输出 schema、副作用、文件哈希或恢复引用等证据 |
| `output/isError` | 兼容旧调用方的文本和错误布尔值 |

工具结果先执行、再规范化和校验，然后才结算账本、检查点、写入租约、PostToolUse Hook 和持久结果。Schema 校验失败不能记成功。外部工具声明的 Schema 与结构化结果在独立 worker 中校验；Schema 最大 64 KiB、最多 64 层，外部结构化结果最大 2 MiB / 100,000 个值，单次校验 3 秒，最多 2 个并发 worker 和 32 个排队任务。远程或文件型 `$ref` 不会加载，超过上限、循环引用或 worker 不可用时均 fail-closed。旧文本工具没有声明输出 Schema 时仍可运行，但必须标为 `not_declared`，不能宣传为强结构验证。

如果写操作已经发生或可能已经发生，而后续校验失败或进程状态不确定，宿主保留写入屏障并要求先核实实际副作用，禁止自动重放。MCP 的 `outputSchema/structuredContent` 和自定义工具声明的输出 Schema 也遵循此规则。

大输出转存与结果结算采用持久化优先：

- 大输出成功转存时必须同时提交恢复索引；转存失败不能把恢复引用伪装成可用。若工具已经完成，仍保留真实 `ToolOutcome` 和 `TOOL_OUTPUT_RETENTION_FAILED` 证据缺口。
- 检查点、写入租约或其他结算阶段在工具执行之后失败时，结果改为 `effect: "uncertain"`、不可自动重试，并保留写入屏障；不能因为结果消息尚未入库就假定工具没有执行。
- 消息持久化失败会回滚该次消息写入，并仅在有界回退条件满足时保存无图片版本；实时通知或界面派发失败不会重复执行工具，也不会再次存储同一结果。
- 永久数据库写失败无法保证结果已落盘。用户或外部客户端恢复时必须先执行真实副作用检查；恢复接口不会把内存中的乐观输出当作已持久事实。

## 办公交付的外部信任边界

宿主办公交付服务可以生成并核验最终文件 SHA-256、结构、公式、渲染和视觉证据。开发者 `/v1` 接口只开放 `prepare` 与 `check` 两个外部动作，并逐阶段重检会话模式、执行环境、`full_access`、工作区相对路径和管理策略。

`visual-batch` 与 `record-visual` 只供桌面任务工作台在宿主内部续接视觉复核。外部调用固定返回 `403 OFFICE_EXTERNAL_VISUAL_EVIDENCE_UNTRUSTED`，不能提交或改写视觉证据，响应不会把外部结果标为 `hostVerified: true`。外部 `check` 可以请求宿主执行受控验证，但必须由宿主生成证据和最终回执，不能由调用方自报通过。

## 计划步骤认领

活动计划以会话现有计划为唯一任务来源。协同工作包应关联同一个 `planStepId`，不能再维护一套无关联的并行任务清单。

认领规则：

| 项目 | 默认值或行为 |
| --- | --- |
| 心跳 | 每 1 分钟 |
| 租约 | 5 分钟 |
| 执行者 | 必须绑定所属会话、`runId` 和授权的 Agent Profile |
| 子任务权限 | 只能认领父级计划明确授权的步骤 |
| 生成号 | 计划 generation 变化后，旧 generation 的迟到回写被拒绝 |
| 并发 | 同一 generation 的同一计划步骤只能有一个未解决认领 |

租约过期只把认领标为 `stale` 并触发核活，不会杀死任务、自动释放或把写操作重新派给另一个 Agent。用户修改正在执行的步骤前应先停止并结算归属运行。无法确认副作用时保持锁定，优先核实而不是抢锁重试。

主 Agent 派发后台 SubAgent 后仍可继续自己的工作，并通过 `wait_subagents` 收集实时结果。父任务继续工作不改变子任务的审批、隔离、计划 generation 或写入租约。

开发者 `/v1` 的 `GET|POST /v1/tasks/claims` 支持 `claim`、`heartbeat`、`settle` 和 `recover`。`claim` 原子绑定步骤 generation、真实 `runId` 和授权执行者；`heartbeat` 只能由匹配的 `ownerRunId` 续租，并会推进 `claimVersion`。直接 `settle` 只接受 `completed` 或 `released`，外部请求必须提交调用方最近读取的正安全整数 `expectedVersion`；缺省或格式错误返回 `400`，心跳等变更让旧读数失效时返回 `409 PLAN_CLAIM_CLAIM_VERSION_CONFLICT`。宿主还要求 active 且有效的租约、仍在聊天运行时存活的精确所有者运行，以及没有活动工具、命令、清理状态、文件租约、执行安全状态或工作区写屏障。`stale` 或 `cancel_requested` 只能通过 `recover` 处理；宿主会确认精确运行已经停止，并核对每个不确定 effect 在最终副作用之后完成的不同只读检查证据，不重新派发写操作。接口仍受管理策略、会话归属和计划 generation 检查，不能用任意 `runId` 伪造认领或替另一个执行者续租。停止请求的 HTTP `202` 只表示 `stopRequested`；客户端必须观察准确运行的终态，不能把 `cancellationConfirmed:false` 当作已停止。

## 数据库迁移与备份

1.3.7 将数据库从 schema 10 升至 schema 11，新增：

- 运行、请求接纳和持久事件。
- 计划 generation、步骤认领和租约。
- Office 交付回执与临时证据索引。

schema 10 升级到 11 前，应用使用 SQLite `VACUUM INTO` 在数据库旁创建 `.pre-v11-backup-<时间>-<随机值>.sqlite` 完整备份。新数据库直接创建 schema 11，不生成空库升级备份。迁移失败时主库仍停在 schema 10，并保留升级前备份。

迁移不重写旧消息、任务或工具历史，也不把旧记录追溯标成“已验证”。复制或 fork 会话时，计划会进入新的 generation，但不复制原会话的活动认领；原所有者、租约和写入屏障不会因为产生副本而改变。

升级后旧 schema 10 程序不能安全打开 schema 11 数据库。回退应用版本前必须关闭应用并恢复升级前完整数据目录或对应备份，不能让旧程序直接覆盖新库。

## 排查顺序

1. 在设置 → 运行与集成 → 运行治理查看有效策略 revision、机器策略和应用策略状态。
2. 策略无效时只修复对应 JSON；不要删除数据库或把项目文件改成 `full_access` 来“绕过”。
3. 运行异常时先读取 `runId`、状态、事件游标和会话快照，确认是失败、中断还是策略阻止。
4. 事件游标返回 `CURSOR_EXPIRED` 时重新取快照，不要复用旧增量。
5. 工具显示失败但可能已有副作用时，先检查文件和外部系统；不要直接重试写操作。
