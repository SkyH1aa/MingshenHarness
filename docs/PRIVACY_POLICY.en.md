# Mingshen Harness Privacy Policy

Effective date: 2026-11-04. Policy revision: 2026-11-04.3. Current application version: 1.3.7. Provider: 新哲文院算法社.

Local code indexes store approved JavaScript/TypeScript, Python, Go, Rust, Java, C/C++ and C# file fingerprints, names/locations, short signatures, reference/call snippets and imports, rather than separate full source copies. Query results can be sent to the selected model as tool output. Structured plans, project plan library, dependencies, breakpoints, checkpoints, confirmed argument hashes and uncertain-operation identifiers remain local. Title full-text indexes and change sequence numbers support local paging/search/synchronization. Saved project plans survive deletion of their source chat and can be removed separately. Session recovery records are removed with the chat; uncertain external-operation workspace barriers need verification before removal. Read caches and temporary leases are process-local. None of these features adds cloud storage. Verification runs declared project checks under current permissions/isolation and preserves output in history. Review project scripts and third-party tools before authorizing execution.

This policy describes actual information handling. New collection features require an updated policy and appropriate authorization.

## 1. Local information

Provider and model settings, encrypted credentials, conversations, attachments, tool output, tasks, imported extensions, browser profiles, traces and snapshots are stored under the current Windows user's application data directory. The standard distribution uses Electron's `Mingshen Harness` data directory, normally under `%APPDATA%`. Managed deployments may use a different configured directory.

The optional companion's display and behavior preferences are stored in local application settings. When the companion is enabled, the main process provides its window with active conversation and run identifiers, states, start times and, by default, titles for the working-conversations panel, menu and conversation navigation. Runs in the same conversation are combined and elapsed time is calculated locally. The menu can still use active status when the panel is disabled. Titles may contain sensitive information and can be visible to people nearby. Turn off **Conversation titles** under **Settings → Desktop experience** and wait for the save to succeed: the companion then receives null titles, and the panel and context menu use anonymous labels. If saving fails, titles may still be visible; retry and confirm the save. Other than titles, the companion window does not receive conversation bodies, file contents, workspace paths, command arguments or approval details. Idle chat uses built-in local phrases and does not call a model or use the network. Conversations opened in Quick Chat continue to follow the existing ChatAgent rules.

Responses history can include provider-issued encrypted reasoning/compaction items, assistant phases and tool-call information stored with the original conversation. These are opaque provider state, not raw hidden chain of thought the application can decrypt, and are separate from safeStorage credential encryption. Replay requires matching provider, model, endpoint and visible content; independent text summaries exclude these opaque items. Approved workspace images read by `view_image` can be stored as image-bearing tool results and sent to the selected image model. PDF page images generated temporarily from attachments retain the bounded-memory rules below, distinct from explicitly read image tool results.

Version 1.3.2 also stores native continuation fields actually returned by the API with the original conversation: native Gemini GenerateContent Parts (including returned thinking summaries, tool calls, optional call IDs and opaque signatures), Gemini Chat Completions message/tool signatures, and DeepSeek Chat `reasoning_content`, Responses plain-text reasoning items and Anthropic thinking blocks with optional signatures. Returned text is not encrypted credential data, and opaque Gemini signatures are separate from application credential encryption. The application does not request or invent hidden reasoning absent from the API response or reconstruct native state from displayed thinking. Validated, bounded, completed state is replayed only to the same provider configuration, model, protocol, endpoint and authentication scope with matching visible text and tool identities, arguments and order. Independent text summaries exclude `provider_state` and opaque signatures; ordinary visible text retains its existing summary rules. This data follows local conversation retention, export and deletion rules, with no new cloud recipient. Review database copies and conversation exports before sharing them.

Images generated in Image Studio, canvas projects and shared image assets are stored under the local application data directory. A generated asset may also store the user's positive prompt, negative prompt, the provider's revised prompt and a bounded provenance version. Only an asset carrying the trusted generated provenance can offer prompt restoration after user confirmation. External imports and legacy records receive no trusted prompt metadata; the application does not guess missing text, and cancelling a restore leaves both current prompt fields unchanged. Generation sends the relevant prompts and explicitly selected reference images to the selected image provider; prompt polishing sends text to the selected language model. These may be different providers and may incur separate usage. If a provider returns only remote image URLs, the main process first downloads the image into bounded memory for the in-app preview using a request that carries no model API key, Cookies or browser credentials, and validates it; the result is not yet written to the asset library. Closing the preview or choosing **Review later** does not immediately discard the candidate, which can be reopened for about 30 minutes. Expiry, an explicit decision not to save or application exit ends its availability. Only explicit confirmation saves the image through the ordinary generated-asset flow and writes its local asset record. Deleting an asset clears its asset record and matching prompts in the legacy workspace backup. The application also attempts to delete the local image file; if the file is locked or the operating system refuses cleanup, it reports a warning and an orphaned image may remain. Data already received by a provider remains subject to that provider's policy.

`browser_screenshot` saves a PNG of the visible page in `browser-captures` under the user data directory and retains screenshot pixels as image-bearing conversation tool history for the next vision-model request to the selected provider. Screenshots are limited to a 2048-pixel longest edge and 8 MiB of PNG data. Without configured image capability, the image is excluded from model requests and an explicit notice is returned. Review the current page for sensitive content before capturing it.

Persistent-command process handles, stdin and output buffers exist only in the current run's memory. Returned commands, output and verification evidence remain ordinary local tool history. Run cleanup stops still-managed commands and awaits closure/container cleanup; command sessions do not resume across restarts. Unconfirmed cleanup retains the local write barrier and lease, and failed cleanup recovery may require restarting; clearing a barrier does not prove process/container termination. `wait_subagents` collects child verification requests. After all tool results from that model turn are saved, checks run sequentially through the parent's existing approval and isolation controls and produce separate results, with records and model recipients following the original conversation's rules.

Conversation and workspace records are not uploaded to a Provider cloud by default. History, archives and snapshots consume disk space. Uninstalling the application may leave data behind. Export or back up needed data before deleting it or cleaning the application directory while the application is closed.

New projects default to Native Memory and may instead select the TencentDB Agent Memory local core at creation. Later conversations, forks, actual children and associated worktrees inherit the choice. Settings → Project instructions and trust lets you select a workspace and change its backend and analysis models before creating a conversation; child and associated worktree selections resolve to the top-level conversation's memory workspace. Related tasks and memory maintenance must finish before configuration changes. Exactly one backend is active at a time, configured in existing local application settings. An explicit switch retains both directories without deletion, renaming, merging or migration. Ambiguous legacy directories or configuration require an explicit selection in Settings rather than an automatic switch. Native Memory may create `.harness-memory/` with explicit preferences, short completed-task summaries, an index and archives. TencentDB uses the pinned upstream L1 scheduling, quality filtering, model extraction/conflict decisions, writer and full-text retrieval. Tencent work/team prompts are not used. The preset excludes Tencent business adapters, OpenClaw, cloud/team services, telemetry, L0 raw-transcript capture, the full L0–L3 pipeline and vector/embedding APIs, and does not contact a Tencent memory service.

TencentDB uses host-committed atomic snapshots in the workspace's `.harness-tencent-memory/records.jsonl` as its authoritative record, bounded to 2000 records / 2 MiB. Upstream product-storage fallback is disabled. SQLite full-text indexing is reconstructed only in memory without another persisted database or automatic archive. Settings can edit existing content or delete records through JSON arrays; explicit memory commands add records. Deletion removes entries from the current snapshot. Both backends allow viewing, search, editing, deletion and disabling automatic maintenance. New runs normally provide compact preferences only, with relevant history returned in bounded excerpts. Native Memory may request a diary summary from the configured conversation model within a 30-second deadline, recorded under Memory usage. TencentDB now uses the workspace analysis model with upstream generic conversation extraction and conflict prompts to distill `persona`, `episodic` or `instruction` records and choose store, skip, update or merge. Only validated structured results are committed atomically. Duplicates and valid empty results add no records, without falling back to full-answer excerpts. Confirmed `persona`/`instruction` preferences are excluded from the mutable conflict store and cannot be rewritten or deleted by this flow; the main chat model must still confirm inferred preferences saved through memory tools. Upgrades and backend switches do not bulk-delete or rewrite old excerpts. Later semantic maintenance can still update or merge unprotected old records, and users can review, correct or delete them. Temporary context and raw dialogue are not saved as a separate memory transcript; original chats retain ordinary session rules.

Actual children can read only the selected memory backend. Ordinary file tools cannot modify memory directories. Child commands use a read-only workspace under both native MXC and Docker, including before memory directories exist. Approved managed file tools may still edit ordinary project files, excluding memory directories. Primary-session command policy remains unchanged; host extensions and stdio MCP are unavailable to children. Read-only Plan does not automatically create or maintain memory. Remote read-only MCP still relies on the provider's declaration rather than an OS containment guarantee. Initialization, model failures, invalid extraction and cancellation do not replace committed snapshots or silently enable another backend.

Disabling automatic memory stops adding new automatic injections and task-memory extraction without deleting existing files. Explicit management commands remain available. Previously sent preferences, diary excerpts and tool results remain part of that conversation's history and may appear in context summaries. Disabling, editing source memory or using `/forget` does not retroactively erase chat content or data already received by a provider. Start a new conversation to stop carrying old history and delete the original conversation as needed. Native archives retain complete original summaries rather than truncating or automatically deleting them; deleting TencentDB snapshot entries cannot erase your own backups. Redaction detects known credential patterns only. Generated memories can be incorrect, with no accuracy or fixed Token-savings guarantee; review and correct them. Memory is ordinary workspace text, not an encrypted credential store, and may be handled by your Git, sync or backup tools. Check tracking before publishing. Model requests still go only to your configured provider; no Tencent or Mingshen memory-cloud recipient is added.

To keep request prefixes stable, the local database stores chronological host-state snapshots, including plans, preferences or relevant diary excerpts used at the time, coding guidance, permissions and diagnostics. These previously sent states can accompany later conversation history to the selected model and do not grant new authorization. The latest state supersedes earlier state without erasing its historical text. Token Saver also stores source-message hashes and reduced replacement excerpts to reuse sent representations, rather than a second complete original chat. Rewinding and rewriting a conversation clears those snapshots and representations; deleting the conversation clears its corresponding records. Original messages and valid summaries retain their own conversation lifecycle. Cache-read, cache-write and reporting-coverage counters accumulate locally without an additional statistics upload.

Cache prefix diagnostics store bounded keyed digests, change categories, block counts and reported usage per conversation and purpose. The key is randomly generated per process and never saved; restart establishes a new baseline. No request text, file paths or API keys are saved in diagnostics or additionally uploaded. Deletion or history rewrites clear the diagnostics while retaining incurred usage. Provider caching settings stay local; supported keys or markers accompany existing model requests, with longer retention explicitly selected by the user. Automatic Gemini / DeepSeek adaptation uses implicit caching without creating billable explicit-cache resources or automatically injecting another provider's cache parameters. Server retention and charges still depend on the selected provider. Recent text requests reused for same-model compaction stay in bounded process memory only, without an additional full disk copy. Existing summary boundaries and recipients remain.

The controlled tool-chain feature only executes static actions already declared in one model response. It is not a general cross-task cache of judgment; every action has separate parameter validation, approval, isolation and records. Results reach the current model in subsequent requests, and failed actions are never replayed automatically.

## 2. Model providers

A separate compaction model may append bounded summary segments. Earlier summaries remain in the existing local checkpoint and accompany later main-model requests until limits trigger merging; original messages are not deleted. Earlier summaries may also provide reference context to the selected primary/backup compactor, with no new recipient. Model family is a local cache setting and does not change models or API protocols; cache keys/markers accompany existing requests. Provider caches are not shared across models; retention and charges depend on the provider.

Sending a task transmits relevant messages, system instructions, attachments, referenced skills, tool definitions, tool results and summaries to your configured Base URL. Provider retention, training, security and international transfers depend on that provider's policies.

TencentDB automatic memory analysis can use a workspace-specific primary model and optional fallback. Without an explicit primary, it uses the model actually running the current primary conversation. Analysis sends the completed current round's user/assistant text only: up to 20 messages, 32,000 characters in total and 8,000 per message, with known credentials redacted. Tool records, attachments, hidden reasoning and earlier rounds are not directly included. Conflict analysis also sends bounded candidate memories. Requests have no executable tools, allow up to 180 seconds per model attempt and incur separately recorded Memory model usage. Primary failure or invalid structure restarts the entire operation from its original input with the fallback, potentially sending the same data range to another provider. Valid empty results do not trigger fallback. You can clear independent model choices or disable automatic maintenance. Configuring a model selects that analysis recipient; already transmitted data cannot be withdrawn. Local memory storage does not imply offline analysis, and no Mingshen or Tencent memory-cloud recipient is added.

These existing requests may also carry approved local image tool results and native Responses, Gemini / DeepSeek state needed for continuation with the matching provider configuration, model, protocol and endpoint. No Mingshen or Tencent recipient is added. Changing configuration or deleting local records cannot retract data already received by a provider.

You may add clipboard images by pressing Ctrl+V in the composer or choosing its right-click Paste command. The application does not monitor the clipboard in the background or read clipboard history. Pasting adds a pending attachment without uploading it. After you send, images follow ordinary attachment rules: they are stored locally with the message and transmitted to the selected model provider. You can remove them before sending.

Uploaded PDF, DOC/DOCX and supported documents can be parsed locally. Scanned PDFs can use bundled offline Chinese/English OCR without contacting an extra OCR service. Extracted text is stored with the local message, sent to the conversation model and may later reach the configured compaction model; at most 120,000 characters are retained with partial-coverage notices. Depending on capabilities, the selected model receives the original PDF or locally rendered numbered page images. Rendered images exist only in requests and a bounded memory cache, not as extra database records. OCR temporary folders contain only bundled language data and are cleaned after completion or cancellation. Encrypted, corrupt or partial input retains explicit limitations; vision/OCR accuracy is not guaranteed. Plan cleanup does not delete historical chats or saved project plans.

`create_document` can generate DOCX, PPTX or PDF in the current workspace. Authoring instructions, tables, speaker notes and target paths are processed within the approved conversation; PNG/JPEG assets first pass through a separate workspace read and permission check and are never fetched from URLs. DOCX/PPTX use bundled authoring libraries, while PDF uses offline Chromium layout. The generated file is saved through the existing write approval, isolation, lease and external-change checks, and overwrite is disabled by default. Generated content is not automatically uploaded to Mingshen or Tencent; if the user sends it to a model, the selected provider's policy applies. System-font availability and layout can vary between Windows machines.

Local-first does not mean local inference. Even local models may have network behavior. API keys authenticate with the selected provider. Their full values are not returned to the UI and should never be pasted into conversations.

Automatic approval is off by default. After you select a reviewer in Settings and enable it for a conversation, the application sends proposed tool names, descriptions, commands, paths and parameters to that model's provider. File-operation arguments may include content to be written. Reviews do not include the entire conversation history or executable tools. Recognized keys and authentication fields are redacted where possible, but not all sensitive data can be identified. The reviewer can use a different provider with its own retention and processing policies. Decisions and reasons are recorded in local activity history. You may return to manual review, clear the reviewer or stop the task; previously transmitted data remains subject to the provider's policy.

At 85% of the conversation model's context window, the application sends older messages, tool arguments and results, any existing summary and text attachment content to a compaction model before the next model request. By default this is the current conversation model. A global default or conversation-specific selection may send historical material to a different provider from its original recipient. Check that provider's policies and your authorization before selecting it. Compaction incurs additional API usage. Summary requests do not resend binary attachment bytes. Parsed documents and text attachments contribute up to their first 120,000 characters; unparsed binary attachments contribute only metadata and paths. Recognized credentials are redacted where possible, but not all sensitive information can be detected. Original messages, summaries and usage state remain local; summaries do not replace or delete original local records. You may stop ongoing compaction or change the model for later attempts; data already sent remains subject to the provider's policies.

You may separately configure a backup approval model and a backup compaction model. If the primary connection fails, times out, loses its stream or returns an invalid result, the corresponding backup is attempted once. A valid denial is not sent to another reviewer to seek approval. The backup provider receives the same category of operation data or historical content, may differ from the primary provider and may incur additional API usage. No backup is configured by default; you may clear it. Configuring it authorizes those transmissions on the stated failures. Stopping, deciding an approval manually or returning to manual mode cancels related review attempts. Failure details may contain redacted, bounded model-response previews stored in local activities or error state; check sensitive content before sharing. If both attempts fail, no operation is automatically granted, no valid summary is replaced and original history is not deleted.

Model requests retry network interruptions, rate limits and temporary server errors up to five times per model request by default, configurable from zero to twenty. Partial output does not reset that allowance; each subsequent independent model request gets its own budget. Retrying sends the current request again to the same configured provider and may incur additional API usage; no new recipient is added. Partial assistant output from a failed attempt is not saved as a complete reply, unfinished tool calls are not executed, and completed local tools are not replayed. Approval and compaction preserve their primary/backup order and total timeouts, with transport retries inside each candidate's logical attempt. The two attempts described above mean the two candidate models. A valid denial is final. Each failure follows existing redacted local logging rules; stopping cancels the wait.

## 3. Browsers, GitHub and MCP

Embedded Chromium may store cookies, sign-in state, cache and site data. Chrome-compatible and Edge-compatible are application profile labels; the application does not bundle the Google Chrome or Microsoft Edge products. Authorized page content may be read by an agent and sent to the selected model.

GitHub credentials enable authorized API and MCP operations. Third-party MCP servers receive tool arguments and may use their own local or remote permissions. Local stdio servers may access host resources. Use trusted sources and minimal permissions. BrowserDo/Embiody uses a separate profile; its own logs, updates and site data are governed by its separate policies.

## 4. Credentials

API keys, GitHub tokens and sensitive MCP settings are encrypted using Electron safeStorage and Windows platform protection. The UI shows masks. Encryption protects storage, not a compromised user account, malicious local process, malicious extension, compromised operating system or deliberate disclosure.

Errors attempt to redact authentication secrets. Third-party error bodies may contain other private information. Review screenshots and logs before sharing them.

## 5. Network, updates and downloads

The skill marketplace requests files and listings from GitHub. After initial consent the application checks dependencies and starts official installation for missing Docker, WSL2 or Embiody, with progress or failure notices. Installation can also be retried in Settings. Download services can see the requester's IP address, timing and requested resources. Windows may require administrator approval or a manual restart; the application does not automatically restart the computer.

Update checks query the latest public release metadata in Supabase at startup and every 24 hours, or when manually requested. From 1.2.6, each confirmed automatic update connects to the publisher's HTTPS ZIP download/CDN service and stages the ZIP and installer in the user data directory's `updates` folder. After verification and active tasks finish, the app closes and launches the installer. Failure or cancellation removes that attempt's cache; an installer handed off for launch remains so the next process can open it. You may delete this cache while the app is closed; old cached installers are never automatically rerun. Legacy download pages can still open in your default browser. Metadata checks use a public application key and send no conversations, source code, user API keys or GitHub credentials. Package downloads send neither that key nor model credentials or browser cookies. Supabase and download services can receive IP addresses, request times and resource paths. Docker Desktop and Embiody have independent telemetry and update policies which Mingshen cannot control.

## 6. Diagnostics

Built-in Token Saver locally reduces model request copies. New configurations disable early turn-count summaries and use Auto response guidance; explicit existing choices and the 85% context safeguard remain. Enabling early summaries uses the configured primary/fallback compactors, with recipients and historical data scope following existing compaction settings and no separate optimization service. Summaries incur usage. Settings, reported token/request counts by purpose and latest estimates/transformation types/source identifiers remain local, without additional full chat copies or automatic statistics uploads. Native state and images contribute only hashes to prefix fingerprints and are not copied into replacement ledgers; their messages retain exact visible content. Recall stays within the same conversation and may reach its selected model later. Deletion clears corresponding records; rewriting history clears stale displays while retaining incurred usage. Disabling the plugin or individual strategies does not undo saved summaries.

Local errors and traces support troubleshooting. Conversations, files and crash reports are not automatically uploaded by default. Diagnostic uploads require an implemented feature, clear disclosure and authorization; an unimplemented upload path is not enabled. Future diagnostics must minimize and redact content and publish a retention period.

Runtime error logs remain in the current user data directory's `logs` folder. They contain timestamps, error sources, HTTP status, related session/run/provider/model IDs and bounded diagnostic details, including primary attempts recovered by a backup and failures or warnings at desktop IPC, local API, background tool, plugin-hook and Office-check boundaries. Logs expire after 30 days and rotate through five files of up to 3 MiB each, totaling at most 15 MiB. A bounded write queue records omission counts during extreme error bursts. Settings and exports summarize retained error and warning records by source and operation, with known omitted and damaged counts; these are neither deduplicated incidents nor all-time totals. New background tool, hook and Office-check diagnostics use bounded state/code metadata rather than deliberately recording tool output or document content. Free text in HTTP error response bodies is omitted only from log copies, retaining status, known diagnostic fields and available stack frames without changing the UI error. Unpersisted omission counts following a write failure remain in the current process until a successful append.

Full conversations, attachments and source files are not attached as logs. Recognized credentials, authentication headers, cookies and echoed request fields are redacted or omitted. Third-party errors or older logs may still expose paths or other sensitive material; redaction is not a guarantee of complete anonymization.

Settings → Runtime logs lets you export JSON to a chosen location and decide whether and with whom to share it. Export does not submit anything to the developer or Supabase. Exported copies are outside application retention controls; protect or delete them yourself. You may delete local log files while the application is closed; future use can generate new logs.

## 7. Exports and shares

Markdown and JSON exports go to your chosen location. The optional local sharing service listens on `127.0.0.1` and offers expiring read-only links. Link holders and programs able to reach that local service may read shared content. Forwarding local ports to the internet changes the exposure and is not a default behavior.

## 8. Your controls

Replace or delete credentials, disable providers and MCP servers, remove extensions, revoke workspace trust, stop tasks, export or delete records and quit the application. Fully quitting stops application tasks. Remove third-party runtimes and revoke GitHub authorizations in their respective products or account settings.

Task completion notifications pass conversation titles and answer previews to the
local Windows notification system by default. They may appear in banners, on the
lock screen or in notification history, subject to Windows settings. Settings →
Appearance can disable previews, sound, taskbar counts or native notifications.
With previews disabled, only the application name and completion text are shown.
Unread state, reply routes and failed reply drafts remain local; Windows may retain
notification content separately. An inline reply is processed as an ordinary message
by the original conversation's chosen model and permissions. No Provider cloud push
service is introduced.

Background manual approvals can also generate native notifications. Previews include the conversation title, tool name and a bounded operation summary, without attaching complete proposed file contents. The same preview control hides these details; approval notifications also have a separate switch. Approve or Reject is processed locally for the exact single operation, without a new cloud review request; its tool result follows the conversation's existing model-transmission rules. Temporary notification/request routes exist only in the current process, expire when handled/stopped/cancelled and cannot restore authorization after restarting. Windows may retain displayed content; disable previews and review lock-screen notification settings for sensitive work.

Background Agent questions and multi-Agent edit conflicts may also create local Windows notifications. Default previews contain redacted, bounded conversation titles and question summaries, which may include mentioned file paths or task information. Disable these reminders independently in Settings → Appearance, or use the shared native notification, preview and sound controls. Activation only opens the matching conversation; it submits no answer, transfers no file ownership and grants no additional permissions. Answers still follow the original conversation's model-transmission rules. Temporary request routes remain in the current process and expire when answered, cancelled, stopped or deleted. No cloud push service or automatic notification-log upload is added. Windows may retain displayed content; clear local notification history or adjust lock-screen settings as needed.

## 9. Children and sensitive information

Minors should use the application with a guardian's guidance. The software does not require identity documents, financial details or a legal name. Do not send sensitive personal data or confidential materials to models, websites or MCP services without authorization.
